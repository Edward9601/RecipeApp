# Python and Django upgrades

Use this guide when changing the Python or Django runtime. An upgrade is not complete just because dependencies install: local development, CI, and deployment each select their runtime independently.

## Upgrade checklist

1. **Set the support policy first.** Decide whether the new Python release is an additional supported version or replaces older versions. Check that the selected Django release supports every Python version the project intends to keep.
2. **Inventory runtime selectors.** Check the CI workflow, deployment platform configuration, local environment, and dependency manifests separately. For this project, `.python-version` selects Render's Python version, while `.github/workflows/django.yml` selects the CI version; changing one does not change the other.
3. **Resolve dependencies in a clean virtual environment.** Check native extensions for wheels compatible with the target Python and platform. Avoid pinning multiple distributions that provide the same import package. Here, `psycopg2` and `psycopg2-binary` were redundant providers of the same import; the Python 3.14 upgrade uses the binary distribution.
4. **Read the framework's release and upgrade notes.** Search application code and historical migrations for removed or changed APIs. A migration may need to remain importable under the new framework even if it was generated by an older release.
5. **Validate both current and fresh database states.** Run Django system checks, apply migrations to an empty database, and run `makemigrations --check --dry-run` against the current models. Use the project's production database engine for validation when possible; a SQLite migration run does not verify PostgreSQL behavior.
6. **Run tests with warnings visible and confirm discovery.** Record the number of tests found. A successful command that finds zero tests is not application-behavior coverage.
7. **Update documentation and all runtime selectors together.** Keep the declared support policy, CI, deployment configuration, and setup instructions in agreement.

## Python 3.14 and Django 6 upgrade notes

This project now targets Python 3.14 and Django 6.1.3. The upgrade exposed these concrete compatibility issues:

- The pinned `psycopg2==2.9.9` attempted a C-extension build and failed on Python 3.14. The project had also pinned `psycopg2-binary`, which supplies the same `psycopg2` import. The duplicate source distribution was removed; the binary distribution and `pillow_heif` were updated to versions whose Python 3.14 wheels resolved and installed in the local environment.
- Django 6 no longer accepts `CheckConstraint(check=...)`; use `condition=...`. The argument appeared in both the current model and an existing migration, so both needed to be updated for the migration history to load.
- Django's migration check identified a model-state difference and generated migration `0047`; keep it so fresh installs and existing databases can reach the same model state.
- An unrelated invalid `from re import T` import in `recipes/admin.py` prevented Django from loading. A startup check found it before tests could run.
- Local validation used SQLite: Django's system check passed, migrations applied, and `makemigrations --check --dry-run` reported no remaining changes. `pip check` also passed. The test runner found **zero tests**, so application behavior remains unverified by automated tests; CI or deployment validation was not run as part of this local check.

See the [Django upgrade guide](https://docs.djangoproject.com/en/6.1/howto/upgrade-version/), [Django 6.1 release notes](https://docs.djangoproject.com/en/6.1/releases/6.1/), and [Python 3.14 porting notes](https://docs.python.org/3.14/whatsnew/3.14.html#porting-to-python-3-14) for release-specific requirements.
